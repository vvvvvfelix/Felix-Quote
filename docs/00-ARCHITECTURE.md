# Felix 企业管理平台 — 架构总纲

> 由「Felix 报价系统 v1.3.0」演进而来。目标：**集团型多组织 ERP + OA 协同平台**，
> 覆盖 公司总部 / 多个工厂 / 办事处 / 国内事业部 / 国际事业部 的完整组织架构，
> 承载每个岗位每天真正在做的事。
>
> 本文是长期演进的"宪法"。每晚迭代前必读，任何改动不得违背本文的分层与约定。

---

## 一、定位与对标

| 维度 | 定位 |
|---|---|
| 形态 | 本地便携版（U 盘/内网可跑），单进程 FastAPI + SQLite，双击即启动 |
| 体量 | 不设上限，模块可插拔，按 Phase 分批落地 |
| 对标 | Odoo（模块化、可插拔应用）、Frappe/ERPNext（DocType 元数据驱动）、用友/金蝶（多组织+多账簿） |
| 借鉴 | Odoo 的"一切皆模块"与依赖声明；ERPNext 的 DocType→自动建表/API/权限；金蝶的多组织（法人/工厂/事业部）三轴模型 |
| 不照搬 | 重型框架、Postgres 依赖、Docker 编排 —— 与"便携双击即开"冲突 |

---

## 二、技术栈（沿用现状，不推倒重来）

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | FastAPI + Pydantic | 已有 15 个模块，路由即模块 |
| 数据库 | SQLite（WAL） | 单文件，便携；重并发场景再议 |
| 迁移 | `core/schema.py` 版本化 `_vNNN(db)` | **只增不删**，每个版本幂等 |
| 前端 | 原生 JS + 单页 `index.html` + `js/pages/*.js` | 无构建链，改完即生效 |
| 运行时 | `runtime/python` 自带 Python 3.13 + 依赖 | 256MB，随包分发 |
| 启动 | `-m uvicorn app.main:app` | 由 launcher 包装 |

**分层铁律**

```
app/core/     基础设施层：db / paths / schema(迁移) / services(单号·审计·待办·状态机) / permissions / crypto
app/modules/  领域模块层：一个业务域一个文件，自带 router，互不 import
app/main.py   装配层：只做 建app + 挂路由 + 启动钩子，禁止写业务逻辑
app/seed.py   演示数据：只灌种子，不参与业务
```

> 模块之间**禁止互相 import**。跨域调用一律走 `core/services.py` 的公共能力，
> 或以 HTTP 调自身 API。这条是长期可维护性的生死线。

## 三、组织主干模型（本项目的地基）

现实中的集团架构是**三轴**的，早期单表 `departments` 撑不住，必须拆：

```
轴1 组织树 org_units    —— 法人公司 / 工厂 / 办事处 / 事业部 / 部门 / 车间 / 班组
轴2 岗位体系 positions  —— 部门 × 岗位 × 职级 × 编制数 × 汇报上级
轴3 人员 users/employees—— 归属组织、任职岗位、生命周期状态
```

### 3.1 组织类型 `org_type`

| 值 | 含义 | 典型 |
|---|---|---|
| `group` | 集团（虚拟顶层） | XX 集团 |
| `company` | 法人公司（独立账套/税号） | XX 制造有限公司 |
| `factory` | 工厂 | 一厂 / 二厂 / 三厂 |
| `office` | 总部 / 办事处 | 公司总部、深圳办事处 |
| `branch` | 分公司 | 华东分公司 |
| `bu` | 事业部 | 国内事业部 / 国际事业部 |
| `dept` | 职能部门 | 行政部 / 人事部 / 销售部 / 物流部 / 研发部 |
| `workshop` | 车间 | 钣金车间 / 装配车间 |
| `team` | 班组 | A 班 / B 班 |

组织树**层数不限**，靠 `parent_id` 递归；冗余字段 `path`（如 `/1/4/9/`）加速子树查询。

> **M001 已落地（迁移 `_v008`）**：权威组织表为 `org_units`，树的层级只由
> `parent_id` 表达，另有三条归属线 `company_id` / `factory_id` / `bu_id`
> 由系统自顶向下自动继承（`core/orgutil.recompute_tree`），让「一厂厂长只看一厂数据」
> 「国际事业部看不到国内客户底价」退化成一次等值过滤，不必在业务代码里写特判。
> 旧 `departments` 表进入**冻结期**：由组织树单向回写（id 对齐），
> 待 M004 完成数据范围改造后废弃。

### 3.2 岗位与职级

- `job_titles` 岗位：董事长、总经理、副总经理、厂长、副厂长、经理、主管、研发工程师、
  技术员、业务员、跟单员、采购员、会计、仓管、质检员、班组长、操作工……
- `job_grades` 职级序列：`M`（管理 M1–M6）/ `P`（专业 P1–P8）/ `T`（技术 T1–T8）/ `O`（操作 O1–O5）
- `positions` 编制：组织 × 岗位 × 职级 × 编制人数 × 上级岗位 → 支撑「编制人数 vs 在岗人数」

### 3.3 人员生命周期

```
应聘 → 入职(probation) → 转正(active) → 调岗/晋升 → 停职(suspended) → 离职(left)/退休(retired)
```

`employee_profiles` 存档案（证件、合同、社保、银行卡、紧急联系人），
`employee_events` 存每一次异动（可回溯，离职账号不删，保留历史单据责任归属）。

## 四、权限模型

两层，刻意不做字段级（成本过高、实际少用），但**成本类字段单列一个权限点**。

1. **功能权限**：角色 → 权限点（`模块.动作`，如 `orders.approve`）
2. **数据范围**：`all` 全部 / `company` 本公司 / `factory` 本工厂 / `bu` 本事业部 / `dept` 本部门 / `self` 仅本人

新增范围：`company` / `factory` / `bu` —— 这是多工厂场景的刚需
（一厂厂长看不到二厂的工单，国际事业部看不到国内客户底价）。

角色库扩到：董事长、总经理、厂长、部门经理、主管、研发工程师、技术员、业务员、
采购、生产计划、仓管、质检、财务、人事、行政、物流关务、只读。

## 七、数据建模约定

1. 表名复数小写下划线；每个业务表必有 `created_at`，有状态机者加 `updated_at`
2. 金额一律 `REAL` + 配套 `currency` 字段；数量 `REAL` 兼容小数
3. 枚举值在模块顶部用 dict 定义（如 `EMP_STATUSES`），**禁止前端硬编码中文**
4. 软删除：`is_active=0`，不物理删（历史单据要能追溯责任人）
5. 每个新模块必须在 `core/permissions.py` 注册权限点，并在角色里分配
6. 迁移：**只追加 `_vNNN`**，禁止修改已发布的迁移函数

---

## 八、前端约定

- 一个页面一个 `static/js/pages/<name>.js`，导出 `render(el)` 与可选 `mount()`
- 页面在 `app.js` 的路由表注册；导航菜单项由**后端下发的权限**控制显隐，不写死
- 表格/表单/弹窗复用 `js/core/ui.js`；请求一律走 `js/core/api.js`
- 视觉：浅色主题、紧凑表格、中文文案；不做花哨动效
- **响应式（M001 前端收尾）**：PC 优先，桌面（≥1100px）布局零改动；手机（≤760px）走抽屉导航（汉堡 `.hb` + 遮罩 `.scrim`）+ 表格转卡片（`.tbl.responsive` + 每 `<td>` `data-label`）+ 触摸目标 ≥40px；双栏页用 `.split-org`（替代写死 inline grid），要隐藏的元素加 `.hide-mobile`。新增响应式规则**只追加**到 `app.css` 末尾、且必须包在 `@media(max-width:760px)` 内，不可改既有断点。详见 `docs/11` / `docs/13`。

## 十、多数据库策略（部署可选）

**原则**：SQLite 是默认且完整可用的后端；SQL Server 作为"真实部署"的可选后端，
通过配置切换，**两套并存、部署时二选一**。

- 后端由 `database.DB_BACKEND` 决定（`sqlite` / `mssql`），读环境变量 `WEIGEAR_DB_BACKEND`。
- SQL Server 连接配置落在 `data/dbconfig.json`（server/port/database/user/password），
  内置默认账户 **root / 88888888**，也支持环境变量 `WEIGEAR_MSSQL_*`。
- `database.get_conn()` 按后端分发；`mssql_config()` 统一读取配置。
- **当前限制**：业务查询仍使用 SQLite 方言（`IFNULL` / `SUBSTR` / `AUTOINCREMENT` 等），
  T-SQL 移植在路线图 **M108** 进行中。因此选择 `mssql` 后端时，应用会拒绝启动并提示完成 M108。
  这一步是"保留两套数据库、部署可选"的接线层 —— 配置已就位，真正可用待 M108。
- 选择建议：≤50 人 / 单机 / 内网 → SQLite（零依赖、便携）；100 人以上 / 需要 HA → 等 M108 后切 SQL Server。

## 十一、报表与打印框架

覆盖每个岗位日常都会碰到的纸面单据与报销凭证，**排版与打印由前端 HTML/CSS
（`@media print`）完成 —— 零额外依赖、所见即所得、直接调起系统打印机**。

| 报表 | 数据源 | 说明 |
|---|---|---|
| 报价单 | 报价管理 | 复用报价单生成打印视图，带公司抬头与水印 |
| 送货单 | 销售订单 | 按订单生成送货/出库单，含收货签收栏 |
| 行程单 | 手工录入 | 出差行程与交通明细，用于差旅报销 |
| 发票 | 手工录入 | **支持 A4 单张 / A4 双联（上下两张 A5）排版**（很多公司的硬性要求） |
| 水单报销 | 影像导入 | 微信/支付宝付款水单截图导入 → 自动排版到合适大小 → **可选脱敏** → 直接打印 |

- 后端模块 `modules/report.py`：报表定义、水单影像归档（`report_slips` 表，含 `mask_json` 脱敏标注）、
  打印数据源。**脱敏**在前端框选矩形（归一化坐标），存为遮罩，打印与预览均生效。
- 权限点：`reports.view` / `reports.edit`（已分配给 财务/销售经理/物流/生产 等角色）。
- 无票单据（微信/支付宝水单）统一走"水单报销"通道，避免手工贴票。

## 十二、授权与试用期

- 试用 **30 天**，从首次安装时间（`settings.installed_at`）起算。
- 授权文件 `.felix_license` 放在 `BASE_DIR`（独立于 `data/`，换库不丢）。
- 授权码 = `base64(json 载荷) + '.' + HMAC-SHA256 签名`（作者私钥内嵌于 `core/licensing.py`）。
  机器绑定：绑定到本机 `install_id`；`"ANY"` 表示通用授权。
- **校验策略**：`get_state()` 实时读取授权文件（含 HMAC 校验），**只在请求进入时算一次，不每请求重算**；
  中间件 `_license_gate` 对「已过期且非永久」的业务接口返回 `402`，放行登录/关于/激活/静态资源，
  保证到期时管理员仍能登录激活。
- 作者签发工具：`tools/license_gen.py`（按 install_id 或 --any 生成授权码）。
- 说明：内嵌密钥属于「提高侵权成本」级保护；真正不可破解需编译/混淆分发（路线图 M106）。
  商用前建议先办软著（见 05-部署与商用保护）。

## 十三、岗位工具箱与系统集成

每个岗位在生产过程中都会用到外部软件/系统，平台以"岗位工具箱"沉淀映射
（`modules/toolbox.py` 数据 + 前端只读页），作为集成规划的单一事实来源：

- 财务：金蝶/用友（凭证导出对接）、电子税务局/税务 UKey（发票抬头税号复用）、发票 A4 双联打印
- 研发/技术：CAD/SolidWorks/AutoCAD（图纸导入资料库+版本）、产品主数据
- 行政/人事：携程商旅/滴滴企业版（行程单/水单导入自动排版报销）、人事档案
- 销售：报价/CRM/邮件（已有）、WhatsApp/企业微信（规划）
- 物流/关务：关务系统/单一窗口、船公司/货代平台（运单导出对接）
- 通用：Office / WPS（资料、报表、说明书模板互通）

集成状态分三档：**已内置**（本系统已实现）/ **可互通**（导入导出或对接）/ **规划中**（路线图已排）。
完整规划见 `docs/06-岗位工具箱与集成规划.md`。
