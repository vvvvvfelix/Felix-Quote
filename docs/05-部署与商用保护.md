# 部署形态、模块开关与商用保护

> 回答三个问题：**有没有更好的部署方案**、**模块能不能按需开关**、**商用/上架/软著怎么保护**。

---

## 一、部署形态选型：四条路，推荐 B

| 方案 | 构成 | 优点 | 代价 | 适用 |
|---|---|---|---|---|
| **A 便携版**（现状） | 自带 Python 运行时 + SQLite，双击 bat | 零安装、可放 U 盘、离线可用 | 单机、并发有限 | 个人 / 单店 / 演示 |
| **B 单机服务化**（推荐） | 自带运行时 + SQLite + 系统服务（Windows 计划任务 / Linux systemd）+ Nginx 反代 | 开机自启、局域网多人访问、部署只要一条命令 | 并发上限约 30–50 人 | **中小公司（10–50 人）主力方案** |
| C 数据库分离 | PostgreSQL/MySQL + 多 worker + Nginx | 并发高、可主从、可备份到秒级 | 要装数据库、SQL 方言要改造、运维成本上去了 | 100 人以上 / 多厂区高并发 |
| D 容器化 | Docker Compose（app + db + nginx） | 环境一致、易迁移、上架云市场方便 | 客户要有 Docker 环境 | 对外售卖、云市场上架 |

**结论：现阶段主推 B，把 C/D 留成升级路径，不提前付代价。**

理由：
1. SQLite 在 WAL 模式下，50 人以内、日增几千单的业务完全够用，性能瓶颈远没到；
2. 换 PostgreSQL 要改 SQL 方言（`IFNULL`/`SUBSTR`/`AUTOINCREMENT` 等），现在改属于**提前优化**，会拖慢业务模块推进；
3. 但**必须把方言隔离在 `core/db.py` 与迁移脚本里**——将来真要切，改动面就只有这两处。这条已作为红线写进 `03-CONVENTIONS.md`。

**什么时候升级到 C**：并发持续超过 50 人、或需要跨厂区实时汇总、或要做秒级备份时。触发条件明确，不用现在赌。

## 二、模块开关（已落地）

- `app/core/registry.py`：模块清单（代号/名称/分组/依赖/是否核心）+ 状态持久化在 `settings` 表
- `main.py`：启动时按开关**动态挂载路由**，单个模块 import 失败只记日志、不停服
- API：`GET /api/modules`（前端菜单据此渲染）、`GET /api/platform/modules`、`POST /api/platform/modules/toggle`
- 管理控制台页面（管理员可见）：运行状态 + 模块开关 + 组织体检

规则：
- 核心模块（登录、平台、组织身份）**不可关闭**
- 关闭时若被其他已启用模块依赖 → 拒绝并提示先关谁
- 开启时若依赖未启用 → 拒绝并提示先开谁
- **关闭只隐藏功能与菜单，数据表保留**，随时可再开启（避免"关了就丢数据"）
- 改完需重启服务生效（路由在启动时装配）

验证记录：默认 113 条路由；关闭 AI 与邮件两个模块后降到 95 条，`/api/ai/capabilities` 确认摘除。

## 三、组织架构跳层（已落地）

小公司没有工厂/事业部层级时，系统不会取到空值，而是自动穿透到最近的有效组织。

- `app/core/orgutil.py`：`effective_parent` / `effective_leader` / `resolve_anchor` /
  `resolve_by_type` / `chain` / `subtree_ids` / `check_integrity`
- 解析优先级：**自身 → 最近有效祖先 → 最近有效后代 → 顶层组织 → 任一有效组织**
- 全部函数**不抛异常、不死循环**（带环检测），异常输入（None/0/负数/不存在 id）一律安全
- 员工创建/更新时部门自动穿透（`identity.py` 已接入）
- `GET /api/org/integrity` 体检孤儿、断链、环——**发现问题不阻断运行，只报告**

测试：`tools/test_orgutil.py`，17 项全通过，覆盖空表、中间层停用、孤儿、成环、无工厂层级、异常输入。

## 四、一键部署（已落地）

```bash
python deploy/detect_env.py                 # 1) 先体检，不满足就给修复方案
python deploy/setup.py                      # 2) 一键配置数据库 + 初始化 + 启动 + 自检
python deploy/setup.py --port 8080 --admin-pass 强口令
python deploy/setup.py --no-start           # 只配置不启动
python deploy/control.py                    # 3) 桌面入口：确保服务在跑并打开控制台
```

- 检测项 10 项：系统、Python、自带运行时、依赖、内存、磁盘、端口、数据目录、数据库完整性、桌面可写性
- 检测不通过**直接中止并给出可执行的修复命令**，绝不硬装
- 部署成功在**桌面**生成 `Felix企业管理系统_部署报告_<时间>.log`
  （访问地址、管理员账号、数据库路径、已启用模块、启动脚本）
- Windows 生成 `【启动服务】.bat` / `【停止服务】.bat`；Linux 额外生成 systemd unit 与 Nginx 配置
- 桌面图标「Felix 管理控制台.bat」→ 自动拉起服务并打开管理控制台（`/#console`）

## 五、软著申请（已落地脚本）

```bash
python tools/gen_softcopyright.py
```

产出 `dist/软著材料_<版本>/`：
1. `源程序_V<版本>.docx` —— 前 30 页 + 后 30 页，每页 50 行，页眉含软件名与版本号
2. `用户手册_V<版本>.docx` —— 由 docs 与模块清单排版
3. `申请信息_V<版本>.md` —— 软件全称/版本号/运行环境/编程语言/代码量（填表用）

软件名与著作权人从 `app/brand.py` 唯一取值，保证程序内署名与申请材料**完全一致**——
这是审查时最容易被挑的点。当前手册页数不足 60 页，脚本会提示补充操作说明。

## 六、商用与上架保护：现状与缺口

**已有的底子**（不用重做）
- `app/brand.py`：著作权人、权属登记号、免责声明、许可声明，全站唯一来源
- `src/LICENSE.txt`：商用许可与禁止行为条款（本次新增）
- `src/【版权与授权】责任声明.txt`：随包分发的声明
- `app/core/crypto.py`：加密基础，可做授权签名
- 构建指纹/归属指纹：`版本.txt` 中已有

**还缺的三件事**（列入路线图 Phase 11）
1. **授权机制**（M105）：机器指纹 → 授权码签发 → 启动时校验 → 试用期限/模块级授权。
   建议复用 `core/crypto.py` 做非对称签名，避免明文比对被直接改库绕过。
2. **完整性校验**（M105）：核心文件哈希清单 + 启动自检，被篡改则告警并拒绝启动关键功能。
   注意别误伤用户正常的二次开发，建议做成「告警 + 可关闭」。
3. **分发形态**（M106）：对外售卖建议编译为二进制（Nuitka/PyInstaller）或只分发 `.pyc`，
   源代码不外发；同时准备 Docker 镜像以适配云市场上架。

**风险提示**
- Python 分发很难真正防逆向，保护目标是**提高侵权成本 + 保留法律证据**，不是做到不可破解；
  真正兜底的是软著登记 + 许可协议 + 侵权取证。
- 商用前务必完成软著登记（下证约 1–3 个月），上架云市场通常要求软著证书。
- 授权与反篡改一定要留「管理员可关闭」的口子，否则客户内网环境误报会直接停摆业务。
