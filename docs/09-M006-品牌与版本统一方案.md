### 1.5 工号前缀与「迁移只追加」公约的冲突（**必须先定方案再动手**）

**冲突**：`WG-EMP-` 的字面量分别落在
- `core/services.py:16` `EMP_NO_PREFIX`（运行时生成工号）
- **`core/schema.py:409/413`（`_v005`）与 `471/475`（`_v006`）** —— 这两个是**已发布的迁移**

按项目公约「迁移只追加，不改已发布的」（`00-ARCHITECTURE` / `03-CONVENTIONS`），
**不能直接编辑 `_v005`/`_v006`**。但若在全新库上只改 `EMP_NO_PREFIX` 而不动迁移，
`init_db()` 重跑迁移链时仍会用旧字面量给 demo_staff 生成 `WG-EMP-` 工号 ——
**M113 重建出来的新库会带着 WG- 工号出生**，WG→WV 这条口径当场失效。

**推荐方案（不动旧迁移，新增一条数据修正迁移）**

1. **`_v005`/`_v006` 保持原样不动**（遵守公约）。
2. **新增 `_v014`（迁移号归属：M006 独占；M113 不占号，其后一律从 `_v015` 起）**，
   在迁移链末尾统一纠正：
   ```sql
   UPDATE users
      SET emp_no = 'WV-EMP-' || substr(emp_no, 8)
    WHERE emp_no LIKE 'WG-EMP-%';
   ```
   迁移链天然按序号递增执行，因此 `_v005/_v006` 先写旧值、`_v014` 再纠正，
   **全新库与老库升级两条路径最终都是 `WV-`**，且旧迁移一字未改。
3. `EMP_NO_PREFIX` 改为 `"WV-EMP-"`，运行时新生成的工号即为新前缀。
4. 顺序保证：`EMP_NO_PREFIX` 与 `_v014` 同一次发布，否则「新旧工号两种前缀并存」。

**偏移量 8 已实测验证，不是推算**（本条曾写错成 9，被纠正）：

| 输入 | `substr(x, 8)` ✅ | `substr(x, 9)` ❌ |
|---|---|---|
| `WG-EMP-0001` | `WV-EMP-0001` | `WV-EMP-001`（吃掉首位数字，工号少一位） |
| `WG-EMP-0021` | `WV-EMP-0021` | `WV-EMP-021` |
| `WG-EMP-1234` | `WV-EMP-1234` | `WV-EMP-234` |

`WG-EMP-` 前缀是 7 字符（W1 G2 -3 E4 M5 P6 -7），序号从第 8 位开始。

**幂等要求（团队负责人拍板）**：`_v014` 必须可重复执行不出错。上式天然幂等 ——
`WHERE emp_no LIKE 'WG-EMP-%'` 只会命中未纠正的行，跑第二次影响行数为 0。
**落地前必须用下面这条断言实测**（含「已纠正的 `WV-` 行不受影响」「非工号值与 NULL 不受影响」）：
```sql
-- 建表灌 4 行：WG-EMP-0001 / WV-EMP-0002 / ADMIN / NULL，执行两遍，结果应完全一致
UPDATE users SET emp_no = 'WV-EMP-' || substr(emp_no, 8) WHERE emp_no LIKE 'WG-EMP-%';
-- 期望：['WV-EMP-0001', 'WV-EMP-0002', 'ADMIN', NULL]（第二遍不变）
```
> **迁移登记处的同样这条分配说明，必须与 `_v014` 一起写进 `core/schema.py`**。
> 但 `src/` 当前处于 QA 冻结期，该笔记与 `_v014` 本体一并留到 M006 实现时落盘，
> 不在本轮动 `src/`（详见 §5）。

> 为什么不直接改旧迁移：改了之后，**老库升级路径**与**全新库路径**会分叉
> （老库跑旧迁移拿到旧前缀，新版跑新迁移拿到新前缀），而迁移内容本身还被
> `build_fingerprint()` 的归属举证依赖。新增一条纠正迁移是唯一公约兼容的做法。

## 2. 可配置化设计（第 2 条的实现方式，不只要改字符串）

### 2.1 现状（决定了改造边界）

- 全项目**没有通用 settings 访问器**：`settings(key,value)` 表存在，但各模块裸写 SQL
  （`registry.py:115/133`、`services.py:84`、`aiapi.py:55`、`mail.py:116`…）。
- `brand.py` 的常量被**装配期**使用：`main.py:27` 用 `brand.PRODUCT_NAME_CN` 拼 FastAPI 标题。
- `brand.py:78` 的 `build_fingerprint()` **对 brand.py 源文件本身取 SHA256** 作为归属举证。
  → 品牌值改成 DB 配置后，**源文件指纹不再反映实际署名**：客户改了公司名而指纹不变，
  这个指纹对外公示就失去意义。这是本次最容易漏的一处。

### 2.2 设计

**① `core/services.py` 新增通用访问器**（顺手收敛现状里那批裸 SQL）
```python
def get_setting(key: str, default: str = "") -> str: ...   # 读不到回落 default
def set_setting(key: str, value: str) -> None: ...          # INSERT OR REPLACE
```

**② `brand.py`：常量保留为出厂默认值，对外一律走 getter**
- 可配置键（**仅此 5 个，白名单**）：
  `brand:product_name_cn` / `brand:product_name_en` / `brand:company_cn` /
  `brand:company_en` / `brand:brand_token`
- **`owner` / `owner_id` 不开放配置**（权属属 L3，见第 0 节边界）。
- import 期不再拼字符串：`APP_TITLE` / `COPYRIGHT_HOLDER` / `LICENSE_NOTICE` 改成函数
  （`app_title()` 等），**getter 绝不在 import 期碰数据库** —— 装配期连接尚未建立，
  且 `brand` → `database` 会引入循环依赖。

**③ 回落保证**：settings 读不到（首装 / 装配期 / 库未就绪）→ 回落常量。
沿用 `registry.is_enabled` 的既有口径：**读不到就按默认处理，绝不把系统起成空壳**。

**④ 缓存**：进程内缓存 + 写入即失效，避免每个请求都打库（关于页、页面标题每页都要读）。

**⑤ 写入路径**：`POST /api/platform/brand`（权限 `platform.manage`）
- 读取端**不新增 GET 路由** —— 设置页直接读现有的 `/api/about`（它本就返回生效品牌值，
  且是公开接口、无鉴权成本）。只加 1 条写接口，把对路由基线的冲击压到最小。
- 若最终需要「恢复默认值」动作，再按需加 1 条，落地时以实测路由数报备。

> **路由基线影响（团队负责人 2026-11-01 定稿）**：当前基线 **186**。
> **H1 / H2 各 0 条**（纯内部日志，不加接口）；**M006 +1 → 187**，**总共 187 定稿，不要 188**。
> 每层落地后必须报实际路由数（H1/H2 各报一次 186，M006 报 187），
> 由团队负责人对齐 QA 的基线，避免复验时误判成回归。

**⑥-关联 · `brand_defaults` 挂进 `/api/about`（团队负责人拍板，取代「恢复默认」接口）**

用户改完品牌值后不知道出厂默认值是什么，就改不回去。解法**不加任何路由**：
`/api/about` 的响应里附带一个 `brand_defaults` 字段，含出厂默认的 5 个键，
设置页在每个输入框旁显示「默认：Felix 企业管理平台」，用户照着改回即可。

- 不新增路由 / 权限点 / 审计面；默认值是出厂公开信息，附在公开接口上**不新增泄露面**。
- 比一键重置接口更安全：那种接口易误触，且要多写一条审计。

> **一个必须守住的边界（与 §2.2 ⑥ 直接冲突，别搞反）**：
> `build_fingerprint()` 聚合的是**生效值**，**绝不能把 `brand_defaults` 也算进去**。
> defaults 是常量、永远不变，一旦算进哈希，指纹就退化成「只对源文件取值」，
> 客户改了署名指纹仍不变 —— ⑥ 的改造当场白做。
> 自测项 T3 必须同时验证这两条：改生效值 → 指纹变；defaults 存在但**不参与**指纹。
- 逐键白名单校验（不在 5 个键内 → 400）、非空校验、长度上限；
- `before/after` 审计留痕；
- 返回最新生效值。前端「系统设置 · 品牌与署名」页 + 关于页即时生效。

**⑥ 指纹改造（关键）**：`build_fingerprint()` 在聚合核心文件 SHA 之外，
**再聚合「当前生效的 5 个品牌值」**，使署名一改指纹即变，保住「对外公示可作归属举证」的原意。
**硬约束：指纹计算不得因读 settings 失败而抛异常导致启动失败** —— 读不到就回落常量，
照样要能算出指纹（自测项 T3）。

**⑦ 装配期标题的已知限制**：`main.py` 的 FastAPI 标题在 import 期取默认值，
改品牌需**重启**才在标签页/接口文档标题生效；页面内展示与单据统计则是即时生效。
这条限制要在设置页写明，别让客户以为改了没生效。

**⑧ 事实来源唯一化**：`database.DEFAULT_COMPANY` 改为读同一个 getter，
与 brand 共用一份值 —— 否则「关于页写一个公司、单据抬头写另一个」。

## 4. 执行顺序与风险

**顺序（团队负责人定，不可倒）**：`H2 → H1 → M006 → M113`

1. **H2 / H1 前置**：只加日志不改行为，零风险；它们是 M006/M113 改常态的观察哨。
2. **M006 在 M113 之前**：M113 是「先改代码 → 再删库重建」。若先重建库，
   新库会按旧令牌（`WG-` SKU、伟格公司名、`VIGEVR`）生成一遍种子，等于白做。
3. **M006 内部顺序**：先改常量与种子（A/B/C/D）→ 再做可配置化（第 2 节）→ 最后验收扫描。
   可配置化放在后面，是因为它要引入 settings 访问器与新接口，属于结构改动，
   与纯文本替换混在一起容易互相掩盖。

**风险**

| 风险 | 处置 |
|---|---|
| `WEIGEAR_DB` 漏改一个测试脚本 → 该测试打到真实库 | 改完 grep `WEIGEAR` **全树零命中**（归档目录与第 3.3 节排除项除外） |
| 改 `tools/test_regression_phase0.py`（QA 的脚本）会动到 QA 的回归基线 | **无需额外协调**：按排期 QA 冻结回归先出报告、M006 在后，不存在边跑边改。落地时按 T1 装防护断言并实测 |
| `schema.py` 的列默认值 `'VIGEVR'` 漏改 | 属 B 类清单，单独列出来就是因为它不在常量区、容易被 grep 忽略 |
| 只改 `EMP_NO_PREFIX`、没处理 `_v005`/`_v006` 里的 `WG-EMP-` 字面量 | 见 §1.5：旧迁移不可改，必须新增 `_v014` 纠正迁移，否则 M113 重建的新库会带着 `WG-` 工号出生 |
| `tools/` 改名漏改一处 | **本轮风险最高项**：失败模式是**污染客户真实库**而不是报错。见下方自测项 T1 的防护断言 |
| 英文型号与 SKU 漏改 | 第 3.1 节的 `-i` + `WG-` 独立项就是为它设的 |
| 改了品牌但指纹不变，归属举证失效 | 第 2.2 节 ⑥ |

## 5. 与 M113 / H1 / H2 的关系

- **M006 与 M113 是两件不同的事**：M006 管「署名与标识符改成什么」（品牌/版本/前缀/词根），
  M113 管「库怎么重建、演示数据换成什么虚构值」。C 类（公司名）两者都会碰，
  **必须由 M006 先定好可配置化结构与默认值，M113 再按其重建**。
- **H1/H2 的动机与 M006 同源**：都是防止「流程按角色配审批人、角色没了就静默秒过」这类
  表面正常的失效。M006 若把角色代码一起清洗了就会触发它，故 H2/H1 排在 M006 之前当观察哨。
- **本轮冻结**：上述全部落在 `src/` / `tools/`，QA 出报告前**一律不改**，本文档只做规划。
  **唯一例外未执行**：团队负责人要求把「`_v014` 归属 M006」的分配说明同步写进
  `core/schema.py` 的迁移登记处 —— 该笔记必须与 `_v014` 本体一起落盘，
  **留到 M006 实现时执行**（见 §1.5 末尾注），本轮不为此破 `src/` 的指纹。
